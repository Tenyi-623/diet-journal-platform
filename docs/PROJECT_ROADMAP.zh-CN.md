**二、第一版边界与职责**

默认目标：本机或授权局域网，50个预创建演示账户，中文／英文／日文界面；支持合成成年用户档案、个人税前年收入档次（日元）、血压记录、偏好与预算输入、一天三餐方案、份量、营养汇总、日元估算、来源、替换一道菜及历史。未登录打开网址进入登录页，无注册功能；登录后进入有今日食谱图片的主页，可进入“用户信息设置”和“聊天推荐饮食”。50个账户不表示50个并发推理。

第一版使用合成数据；不通过收集真实患者信息来验证系统。复杂合并症、妊娠、未成年人等是否提供定量计划，由支持范围和经过审核的规则决定；未支持的情况返回解释/待补充信息，而不自动套用普通成人方案。该限制是项目范围决定，不是医学指南分类。

职责：后端确定资料是否足够，执行约束、计算营养和价格、选择并验证菜谱；检索提供证据；模型辅助理解输入、查询翻译和解释。展示数字与来源由后端绑定。输入和检索文档都是数据，不是授予模型额外权限的指令。

**本次确定的产品需求**

- 账户：仅使用本地PostgreSQL内预创建的50个用户，登录ID＋密码登录；不提供自助注册。数据库实际保存密码哈希，不保存明文密码。
- 收入：用户选择个人税前年收入档次，币种JPY，按年；不要求输入精确收入。它用于默认饮食预算和价格偏好，不决定健康所需的营养目标。
- 首页：登录后展示“今日推荐”的食谱图片卡片及“用户信息设置”“聊天推荐饮食”入口。
- 聊天：支持饮食及为饮食推荐补充信息的对话。确认无关时，回答正文必须逐字为“无法回答与饮食无关的内容”，没有额外标点、前后缀、理由或引用。该固定中文句在三语界面下保持不变。
- 本次仅修订规划，未创建账户、修改数据库表或实现页面。

**步骤1：冻结需求和验收样例（P0）**

工作：写明每种输入及对应行为；区分“一天三餐”“单餐替换”“食物营养查询”“饮食知识问答”。先不做自由生成七天菜谱、照片识别、实时商城价格和自动诊断。明确预算是每人每天的食用成本还是实际采购支出，第一版建议采用前者并另列采购量。

交付：需求文档、10–15个合成角色、20个验收场景、范围外场景清单。覆盖收入档次、偏好、过敏、缺档案、预算无解、数据缺失、三语同义请求、冲突输入、今日食谱首页、无注册及饮食话题限制。

验收：每个场景均能判断应该生成、追问、拒绝覆盖范围之外的请求，还是报告约束无解；不依赖“看起来合理”。

**步骤2：建立工程基线与可恢复环境（P0，依赖1）**

工作：检查并建立Git管理，排除.env、密码、个人资料、大型原件及模型；固定Python/前端依赖和模型名称、digest；保留原数据哈希清单。引入顺序数据库迁移，保持已有表和ID；建立独立测试数据库。为数据库做完整备份并在测试库实际恢复一次。已有“intermediate”备份不能当完整最终备份。

后端按配置、路由、服务、数据访问、schema分层；原有功能逐步迁移，不立即大改所有文件。已有psycopg足够，不必为使用迁移而强制改为ORM。

交付：环境示例、迁移脚本、初始化命令、测试库、备份/恢复说明。

验收：从干净环境可重建表结构，测试不会修改演示库；恢复后食品、来源、片段计数与抽查内容一致。迁移账号与运行账号权限分离。

**步骤3：定义领域模型和API契约（P0，依赖1–2）**

需要增加的实体：users、sessions、profiles及其版本、income_bands、income_budget_policies、blood_pressure_records、profile_allergies/preferences、food_aliases、allergens/food_allergens、recipes/recipe_ingredients、recipe_assets、price_observations、diet_rules/rule_versions、recommendation_jobs、recommendations及输入/数据/计算快照、daily_recommendations、recommendation_citations、chat_sessions/chat_messages、feedback。沿用现有食品和知识库来源表，不复制营养事实。

外键始终包含食品dataset_id，避免不同版本的相同食品编号混用。现有食品库只按Excel哈希唯一，需升级为源文件哈希＋解析器版本＋审核版本的发布标识，支持draft/active/superseded/quarantined与回滚；原文件不变但解析逻辑修正也能发布新版。历史记录保存当时的资料、规则、食品/价格版本、计算结果、引用原文和文档版本；不能只保存可被更新的当前行ID。

统一单位：身高cm、体重kg、血压mmHg、食用量g、能量kcal、钠/钾mg、食盐相当量g、货币JPY；记录测量时间、时区和资料更新时间。响应区分ready、needs_clarification、out_of_scope、unsupported、infeasible、failed，任务状态另含queued/running/cancelled。out_of_scope用于饮食话题之外的请求，unsupported用于属于饮食但超出已审核支持范围的请求，二者不能混用。

建议接口（均为待开发）：POST /api/auth/login、POST /api/auth/logout、GET /api/me；GET/PATCH /api/profile；GET/POST /api/blood-pressure；GET /api/foods、GET /api/foods/{code}?dataset_id=…；POST /api/recommendation-jobs、GET /api/recommendation-jobs/{id}；GET /api/recommendations、GET /api/recommendations/{id}；POST /api/recommendations/{id}/substitutions；POST /api/qa；GET /api/income-bands；GET /api/home/today；GET /api/recipes/{id}；POST /api/diet-chat/messages。饮食聊天消息携带所属会话ID和上下文，返回领域状态或推荐任务ID；饮食问答与聊天共用话题判定服务，不能留下通用问答绕过入口。明确不提供注册API。创建任务接收幂等键，身份由会话读取。

验收：请求/响应有Pydantic schema、错误码与示例；同一请求可被前端mock、后端和测试一致解释。

**步骤4：实现登录、权限和用户资料（P0，依赖3）**

工作：在本地PostgreSQL预创建恰好50个具有唯一登录ID的演示用户，每个账户使用独立初始密码，表中只存Argon2密码哈希。初始化命令幂等，不重复创建账户，也不覆盖用户已经修改的密码。提供改密、禁用和退出；忘记密码由本地管理命令重置，不增加公开注册或建号流程。浏览器建议同源部署、服务端会话、HttpOnly/SameSite Cookie；HTTPS部署使用Secure；写操作加入CSRF/Origin校验。若选JWT，不把健康资料放入payload，另设计失效和撤销。

档案采集实际用于规则的最少信息：年龄、身高体重、活动水平、目标、食物过敏、偏好、地区、个人税前年收入档次（日元）、预算、烹饪条件；疾病和必要用药信息是自报、非系统诊断。年龄及数据时间要能回溯；用于能量公式的生理参数缺失时追问，不根据姓名推断。

区分unknown、none、present，尤其“未填写过敏”不等于“无过敏”。自然语言发现新的过敏信息时，当前请求先按限制处理并要求确认档案；用户一句“忽略过敏”不能覆盖已有过敏记录。

验收：未登录访问根路径显示登录页，直接访问受保护子页面跳转登录，业务API返回401；有效会话可进入主页。不存在注册链接、注册页或注册API。预建50个用户可登录，未知ID不可登录，初始化重复执行不新增账户/改密。用户A不能访问B的档案、收入、聊天、血压、推荐任务、历史或引用入口；管理操作权限明确；退出/禁用立即影响会话；日志不记录密码、收入档次和完整健康档案。

**步骤5：建立食品的“可推荐子集”（P0，依赖2–3，可与4并行）**

先选择约50–100种覆盖主食、蔬菜、蛋白来源、乳品/替代品、油和调味料的常用食品。此数量是实施目标，实际以可行菜谱覆盖为准。

补充日文标准名及人工核对的中英别名、食品类别、原料/熟食状态、份量范围、可食部口径、适用烹饪方法。审核完整配方的过敏原，复合食品不能仅通过名称关键词判断不含某过敏原。食品成分表不提供可靠的品牌交叉污染保证。

建立per-food/per-nutrient质量状态：原值、数值/Tr/缺失、估算标记、脚注、是否允许参与某种约束。缺失不能填0；Tr没有经确认的上界时不能用来证明精确硬上限合格；数值0也需保留来源精度。独立星号和未解释脚注需先核对，或从对应约束候选中排除。

营养字段固定选定一种适用口径：不能把两种蛋白质、几种碳水项或钠与食盐相当量相加。优先采用官方能量字段，不能默认4/9/4重算后覆盖。

交付：推荐食品白名单、营养字段映射表、别名和过敏原审核记录。

验收：抽样涵盖三种状态（生/熟/加工）、mg/μg/g、零/Tr/括号/缺失；可推荐食品所需关键字段和过敏原信息完整或明确排除；01210继续隔离。

**步骤6：补齐可执行的菜谱和份量（P0，依赖5）**

建立约20–30个受控菜谱模板。每个模板包含recipe_id/version、材料food_id、可食重量、调味料、份数、成品重量/损耗依据、做法、设备、用时、可调整份量和过敏原汇总。另关联本地图片资产，记录路径、来源/使用授权、替代文本、是否示意图及对应菜谱版本。图片内容应与菜谱名称、主要食材和做法相符；份量以经过计算的文字为准。缺图显示统一占位图，图片失败不能隐藏营养和过敏信息。

每条菜谱只能采用一种一致核算路线：按对应熟食品条目和熟重，或按原料及已验证的烹调产率/保留率；不能把熟重直接乘生食物营养，不能用熟食条目后再重复扣烹调损失。没有可靠烹调数据时收窄支持菜谱。

不能遗漏油、酱油、盐、汤汁等；“用了多少”与“实际吃下多少”有区别，第一版明确模型假设，不能声称精确到真实吸收量。

验收：人工手算若干标准份量和两倍份量，核对整道菜、每份和每100g；过敏原由所有材料继承，替换原料需要重新计算。

**步骤7：建立价格、地区与收入预算策略（P0，依赖3–6）**

用人工整理、注明日期和来源的本地价格或明确标为演示数据的价格。字段包括食品/商品映射、地区、商店/来源、日期、包装净重、可食率、税口径、JPY价格、有效期和估算标志。不得让模型编价格或将未知价格当0。

分别计算食用成本和采购支出；采购量按包装向上取整，并汇总重复原料。原料采购价不能直接套到熟食100g重量；需有产率换算。第一版不要求实时抓取超市。

收入档次建议先采用以下可配置产品分组；这些边界是毕业演示的初始设计，不代表官方收入统计分组。用户已确认个人税前、年度、JPY口径，尚未确认具体档位边界。

| 档位ID | 页面选项 | 数据库存储边界（JPY，左闭右开） |
|---|---|---|
| JPY_A1 | 不满200万日元 | [0, 2000000) |
| JPY_A2 | 200万～不满400万日元 | [2000000, 4000000) |
| JPY_A3 | 400万～不满600万日元 | [4000000, 6000000) |
| JPY_A4 | 600万～不满800万日元 | [6000000, 8000000) |
| JPY_A5 | 800万～不满1000万日元 | [8000000, 10000000) |
| JPY_A6 | 1000万日元及以上 | [10000000, 无上限) |

profiles保存annual_income_band_id、收入分组版本和更新时间；income_bands保存币种JPY、period=annual、scope=personal、basis=pretax及端点。未填写保持unknown，不自动视为零收入。页面不向用户贴“贫困/富裕”等标签。

映射链路：收入档次→版本化预算策略→默认每日每人食用预算建议/价格偏好→通过健康和过敏约束的菜谱筛选排序。每条income_budget_policy包含档位、地区、建议预算上下限、默认预算、成本偏好、适用条件、版本和依据说明。各档的具体预算金额在本步骤用已核对的本地菜谱成本校准后确定；未完成校准和发布的策略不得自动生效，不能让LLM即时编出预算，不能把税前年收入按固定比例直接称作可支配食品支出。

实际采用预算的优先级：本次用户明确预算＞档案中用户设置的预算＞已发布收入档次默认预算。收入仍记录为背景信息，显式预算一致时不强行推荐不同价格的菜单。低档位优先性价比，高档位增加可选食材范围但不以花完预算为目标；收入不改变应满足的健康目标、必要营养或过敏限制。预算是否硬上限由用户选择，价格可靠性另行标注。

首次设置展示收入档次带来的预算建议并允许调整；用户确认整份档案后启用。缺收入且无显式预算时，提示补充收入或直接设置预算，不提供伪装成收入个性化的结果；仍允许一般饮食知识问答。收入/预算更新使今日推荐失效重算，历史保留原收入档次、实际预算、来源（request/profile/income_policy）和策略版本。

验收：收入边界不重叠也不遗漏；同一健康档案改变收入会选择对应预算策略，但不会改变健康目标；本次预算正确覆盖默认策略；未发布策略和缺价不能伪装已满足预算；预算无解不放宽健康/过敏约束。同样配方不同份量可复算。

**步骤8：整理证据与结构化饮食规则（P0，依赖1、5；与6–7并行）**

先列出第一版实际使用的规则清单，再复核相关指南段落和表格；不必为演示先OCR所有尚未使用的页面。每条规则保存指标、单位、比较运算、适用人群、排除条件、所需资料、时间尺度（日/餐）、来源、PDF物理页码/印刷页码、表格位置、版本、生效状态及审核者。

区分一般膳食目标、疾病管理建议和个体医嘱。BMI是一个指标，不能单独推导全部能量和营养目标；没有信息就追问或仅返回一般知识。肾病、血钾及用药等信息不足时，不能自动给所有高血压用户加“高钾”规则。血压记录用于展示与受控分流，不由单次测量自动诊断或改药。

高血压解读文章不能代替全文；更完整资料先确认合法获取及允许的引用/使用范围。日本高血压学会公开页面对指南下载、复制及利用设有限制，不能把网页可看等同于可批量入库：https://www.jpnsh.jp/guideline.html 。DRI官方材料：https://www.mhlw.go.jp/stf/newpage_44138.html 。

毕业演示可由导师/领域人员核对引用和适用条件；未获得专业临床审核的规则标为演示规则，不能据此报告临床有效性。范围外病例展示安全退出分支。

验收：每条启用规则均有可核对来源和适用条件；关键数字由表格/原图核对，不直接采用OCR；冲突不自动取更严格的一条，优先检查适用性，无法消解则暂停个体化推荐。

**步骤9：实现营养与费用计算服务（P0，依赖5–8）**

先用确定性函数完成计算，不接模型。成分量=每100g可食部含量×对应可食重量/100，逐材料汇总到菜、餐、日。营养量和成本使用适当精度，先累加后显示取整，边界判断不使用已显示的四舍五入值。

钠与食盐相当量统一但不重复计算：换算展示时食盐g=钠mg×2.54/1000；来源为食品PDF第30页、印刷页25。官方盐当量与由已舍入钠值换算的数可能略不同，应保存采用的口径与精度。

输出包含数据完整性、未知字段、估算标记和计算明细。测试边界份量、单位误输入、生熟不匹配、重复原料、跨数据版本和NULL值。

验收：约20个手工核对样例达到事先规定的数值精度；单位/来源状态不能丢失；关键字段不确定时不能返回“满足全部限制”。

**步骤10：实现约束筛选与一天三餐规划（P0，依赖6–9）**

按顺序处理：话题与请求类型判断→档案/请求完整性→支持范围→解析显式预算或收入档次默认策略→硬约束过滤→枚举受控菜谱及离散份量→计算日总量→检查硬约束→按偏好、营养偏离、费用、用时、多样性等软目标排序。主页今日推荐直接调用同一规划器，不能绕过个体约束。

预算是否硬约束由用户选择；过敏及适用的硬性限制不能由排序分数抵消。菜谱/份量候选有限时先用可解释的搜索，规模和时间实测不足再选优化求解器，不必第一天引入复杂模型。

返回最优可行方案及原因；无解时返回明确冲突和可调整项，只有用户改变约束后重新生成。不能为凑答案默默放松限制。相同版本和输入下算法需可复现，平分项有稳定排序。

验收：至少包含可行、预算无解、过敏无解、缺少关键营养值、超范围档案五类；所有被接受方案用独立检查函数再验硬约束。此时不依赖LLM也应能生成结构化的一天三餐。

**步骤11：完善三语检索和引用（P1，依赖8；可与9–10并行）**

先检查当前按字符窗口切分的片段是否跨越标题、例外条件或参考文献；仅对检索失败的部分改进为标题/段落感知切分，建立新版本并回归，不能把现有切分宣称为已验证的语义分段。按图实现原问题与日语译文双路向量查询；保留原问题、译文、翻译状态和检索版本。翻译验证否定词、过敏原、疾病名、单位和数值，失败时可降级原文查询或追问。

比较原文检索、日语检索和双路融合三种方案；以RRF等可控融合方法开始，先按chunk_id去重再处理相邻重复片段，不能未经评测强行认定双路一定更好。过滤不适用版本、人群、隔离来源；评估过期或解读资料的使用范围。

建立至少30个语义场景×3语种的冻结测试集（90条），再分开发集与未参与调参的测试集。人工标注可回答性、相关来源、页码和关键事实；包含无证据问题、翻译歧义与合并症。临床内容标注需要相应领域审核。

现有规模先保留精确向量搜索作为基线；以后只在量级、延迟证明有需要时启用HNSW，并测试过滤后召回数和精确基线差异。pgvector参考：https://github.com/pgvector/pgvector 。

验收：记录每语种Recall@k、来源适用性、无答案识别、错误翻译、引用正确率及延迟；阈值先在验证集选择，不能把相似度当医学置信度。

**步骤12：接入模型理解、解释及严格输出检查（P1，依赖10–11）**

先在后端加入统一的饮食话题判定，位于知识检索、Embedding、菜单规划和回答生成之前。分类可用受限模型调用辅助，但后端决定分支并返回固定话术，不能只在system prompt中要求拒答。

| 对话情况 | 处理方式 |
|---|---|
| 食谱、食材、营养、做法、饮食费用、饮食相关健康限制 | 进入对应饮食流程 |
| 为推荐补充“我的收入属于第二档”“我过敏”等资料 | 视为饮食上下文信息，必要时确认档案更新 |
| “换一个”“太贵了”“不要鱼”等接续语 | 结合本用户当前会话和方案判断，不能按孤立关键词拒绝 |
| 明确要求股票分析、无关编程、娱乐等 | out_of_scope，正文仅为“无法回答与饮食无关的内容” |
| 同时要求饮食与一个独立无关任务 | 第一版采用严格策略，整条请求返回同一固定句；背景叙述如“工作忙，请给我快手早餐”不属于此类 |
| 含食物词但真实任务无关，例如“用苹果写一个排序程序” | 仍判定out_of_scope |
| 属于饮食但超出已审核人群/能力 | unsupported或needs_clarification，不误报无关 |
| 话题不确定或分类服务失败 | 请求澄清或返回服务暂不可用，不回退成通用聊天 |

out_of_scope由后端常量生成，响应不附菜谱或引用；前端不翻译、不拼接欢迎语或其他正文。这一规则优先于普通“按用户语言回答”的产品设置。用三语输入、提示注入、混合请求和上下文省略做回归；不能用单词白名单或向量相似度单独判断是否相关。

通过话题检查后，把自然语言解析为受限schema（目标、偏好、预算、请求类型、待确认冲突），不能让模型静默修改长期档案。规则产生结构化目标，规划器提供已合格的方案，RAG提供可引用证据，模型只在此范围内解释。

使用Ollama JSON Schema输出并在FastAPI用Pydantic再次校验；当前安装模型的支持情况必须本机验证。官方机制：https://docs.ollama.com/capabilities/structured-outputs 。格式合法不代表事实正确。

检查food/recipe ID是否在候选中、份量是否允许、数值是否与计算服务一致、引用ID是否属于本次检索、引用能否支持对应陈述、回答语言是否正确。医疗目标只引用已启用规则。源ID映射真实页码由后端完成，模型不能编页码。

错误最多有限次修复（例如1次），仍失败则使用确定性模板解释已验证方案，或明确失败；未通过校验的推荐不能先流式展示给用户。普通知识问答走不同schema，不附带自动生成的个人治疗建议。

验收：构造虚构ID、超份量、编造页码、篡改钠值、语言错误等输入，均无法作为有效方案发布；模型不可用时不会回退成无约束chat。

**步骤13：任务编排、历史和替换（P1，依赖4、10–12）**

将生成作为持久化任务：创建→queued→running→成功/需补充/无解/失败/取消。可以先用PostgreSQL任务表和单独worker，不强制增加Redis/Celery。定义租约、超时、重试上限、幂等键和进程重启后的恢复，避免只有进程内BackgroundTasks导致任务丢失。

任务保存档案快照（含年收入档次）、实际预算及来源、收入预算策略版本、约束、规则/数据/价格/模型/prompt版本、候选、证据、计算和校验结果；日志脱敏。只对所属用户可见。

“换一道菜”以当天剩余约束重新规划，重新验全天总量和预算，不仅比较替换菜的单项热量。新方案保存新版本，不覆盖旧结果。

验收：双击不会创建重复方案；任务重启能恢复或明确失败；历史数据不会因后续食品或指南更新而悄悄变化；替换后全部约束仍成立。

**步骤14：实现React三语界面（P1，依赖3；骨架可与后端并行）**

采用架构中的React、TypeScript、Material UI与Vite。用户页面与路径规划如下，不提供注册页：

| 路径 | 页面与行为 |
|---|---|
| / | 未登录进入/login，有效会话进入/home |
| /login | 登录ID、密码、登录按钮及简洁错误提示；没有注册链接 |
| /home | 今日食谱图片卡片；醒目的“用户信息设置”“聊天推荐饮食”入口；另有历史和退出 |
| /profile | 个人资料、健康限制、过敏、个人税前年收入JPY档次选择、预算建议与手动调整；保存后重算相关推荐 |
| /chat | 饮食聊天、上下文、澄清、推荐任务状态、方案及固定无关回复 |
| /recipes/:id | 图片、配方、做法、适用份量、计算值、费用和来源 |
| /history | 当前用户的历史方案与详情/替换 |

所有受保护页面与API都鉴权；前端路由拦截不能替代后端权限。

主页的“今日”按Asia/Tokyo日期定义。资料齐全时使用通过同一健康/过敏/预算校验的方案，展示例如3–6张图片卡片（可配置）。数据契约包含recipe_id/version、图片、名称、餐次、份量、费用及是否个性化；点击进入详情，不能仅展示无对应配方的图片。

首次登录资料不足时仍可展示明确标为“食谱示例，完善信息后生成个人推荐”的图片卡片，并提示去设置资料；不得称为已适合该用户的今日推荐。已有已知过敏条件仍需过滤。无法保证适用时用占位卡或补充资料提示，不能强行显示为推荐。

今日结果按user_id、东京日期、档案版本、实际预算/收入策略版本、食品/菜谱/价格/规则版本缓存；输入变更或跨日触发失效。现有聊天中临时提出的预算只作用于该请求，用户未保存到档案时不自动改变主页默认预算。重复刷新不能不停调用模型。

UI文案用翻译资源管理，食物别名独立审核，原文引用保持日语并标注翻译。正常饮食回答语言可当次覆盖默认语言；无关内容固定中文句“无法回答与饮食无关的内容”不做翻译。明确g、mg、每人/每天、可食/采购重量；给用户展示限制来自何处及资料缺失项。

结果卡片显示菜谱、份量、计算值和估算状态、理由、来源、替换按钮。引用链接由授权文件服务提供，不能直接暴露服务器路径或任意文件读取；有版权限制的原件仅在允许范围内呈现。

验收：三语操作流程完成；刷新/返回后状态正确；窄屏可用；加载、排队、无解、需要补充和失败有独立界面；表单可键盘操作，错误定位明确。

**步骤15：统一部署、隐私与故障控制（P1，依赖4、13–14）**

用Caddy或Nginx统一提供构建后的页面和/api，最终只开放受控入口；数据库与Ollama保持回环/内部网络访问。Ollama本地API不自带认证，不能因为Web有登录就把11434开放到局域网。官方说明：https://docs.ollama.com/api/authentication 。

逐步把API、worker、proxy加入Compose；现有Ollama可继续在宿主机/原容器，不必迁移模型。容器中的127.0.0.1不是宿主机，明确连接地址；ARM64兼容性及GPU接入在目标机器验证。开发依赖与演示启动分开，不依赖终端存活。

设置连接池、请求长度与并发限制、推理排队、超时、任务取消、有限重试；LLM与embedding共享机器要实测内存及模型装卸影响。不要通过无上限增加Uvicorn worker解决GPU推理排队。

区分liveness、数据库readiness和模型可用状态。用户错误消息不返回底层异常、路径、配置和个人数据。保护或关闭公开/docs、embed及开发chat入口，所有业务API统一鉴权。限制跨域、预防SQL注入、对模型文本做安全渲染，文档和用户输入中的指令不能获得访问其他用户数据或执行代码的能力。

针对提示注入、敏感数据泄漏、未验证输出和资源耗尽做测试，参考OWASP：https://genai.owasp.org/llm-top-10/ 。保证来自后端权限和校验，而非单靠system prompt。

验收：局域网无法直接访问DB/模型；另一账号访问被阻止；服务重启可恢复；模拟模型宕机、DB不可用、队列满和缺少价格时表现明确；备份可恢复。演示库使用假资料，论文截图避免真实隐私。若将来转真实用户服务，需另行确定同意、保留/删除、适用地区法规与专业审核要求。

**步骤16：端到端评测、论文实验与最终交付（P0发布门槛，贯穿全部阶段）**

验证矩阵：

| 方面 | 必须记录和通过的检查 |
|---|---|
| 权限 | 仅50个本地预建用户可登录，初始化幂等；无注册页面/API；未登录直达子页面和业务API均受保护；跨用户档案/收入/聊天/任务/历史/引用越权全部拦截 |
| 收入与预算 | 区间端点、策略版本、收入变化、显式预算覆盖、缺收入/未发布策略、无解、历史不变；收入不改变健康目标 |
| 今日首页与图片 | 图片绑定真实菜谱版本；资料不足显示示例；已知过敏过滤；缺图占位；按东京日期跨日更新及档案变化失效 |
| 话题边界 | 三语无关请求均精确返回固定中文句；无附加内容；上下文短句和资料补充不误判；混合请求按约定处理；分类故障不开放通用聊天 |
| 营养计算 | 标准样例、单位、舍入、份量、缺失、估算、生熟换算 |
| 推荐约束 | 在冻结测试集中，所有发布方案硬约束违规数为0；并报告无解率和有效方案覆盖率 |
| 引用 | 无虚构文档/页码，引用可定位；另外人工评估“证据是否支持陈述” |
| 多语言 | 每语种分别报告召回、语言正确性、关键实体和否定词保真 |
| 故障 | 模型/DB/网络失败、重试、重复提交、取消与服务重启 |
| 性能 | 区分冷启动/热模型，测试1、2、5并发后再决定容量；记录排队、检索、规划、生成P50/P95 |
| 可重复性 | 固定模型digest、数据/规则版本、请求集；重复运行有可追溯日志 |

“测试集0违规”不是对所有未来请求的医学安全证明。不要只报成功返回率：一个总返回无解的系统也可能0违规，所以还要报告覆盖率与不必要拒绝率。只有内部一致性检查不能证明临床有效性。

论文比较：纯模型回答、RAG回答、结构化规则/计算+RAG+模型解释；仅对合成案例离线评测，未经约束的基线不对真实用户展示。检索消融比较原语种/日语翻译/双路；可选比较无重排/重排与精确/HNSW，后两项只有实际实现才报告。开发集和测试集分开，不在测试集挑prompt再报告同一结果。

评审量表包括约束违反、数字可复算、引用支持、菜谱可执行性和用户偏好匹配；人工评价至少标明评审人数、资格和一致性，不用LLM自评分作为唯一依据。血压改善或治疗效果需要独立研究，不能由离线系统实验得出。

交付：能一键启动的代码和演示数据、数据库迁移、架构图更新、API文档、数据字典、规则及来源清单、安装/备份/恢复说明、冻结测试集和评测报告、演示脚本/视频、明确局限。

**三、推荐实施顺序与阶段门槛**

依赖主线：范围与数据模型→推荐食品/菜谱/价格→规则和计算→无模型三餐规划→检索和模型解释→前端整合→部署评测。账号与界面骨架在API契约确定后可并行；RAG评测可与菜谱规划并行。可先在已审核的小食品集合完成整个流程，再扩展覆盖，不以全部2477种自动可推荐为首版目标。

**四、答辩可直接使用的完整演示脚本**

1. 打开网址显示登录页，确认没有注册入口，用本地预建账户登录。
2. 进入主页查看食谱示例图片和两个主入口；打开“用户信息设置”，填写合成资料、过敏、偏好，选择个人税前年收入（日元）档次。
3. 查看该收入档次的默认预算建议，可手动调整；保存后主页显示通过个体约束的今日食谱图片，点击查看配方。
4. 进入“聊天推荐饮食”，输入饮食需求，展示三餐、重量、营养、费用和真实来源；缺信息时先补齐。
5. 输入“推荐几部电影”，界面仅回复“无法回答与饮食无关的内容”；用英/日语无关输入重复验证同一句中文。
6. 输入“太贵了，换一个”，验证系统理解当前菜单上下文；改变档案收入后核对预算策略与主页缓存失效，健康目标不变。
7. 查看日语原文和真实页码、Excel出处；换一道菜后展示全天重算；低预算无解时不放宽过敏条件。
8. 退出后用另一账户登录，验证档案、收入和聊天互不可见；展示重启恢复及评测报告。
