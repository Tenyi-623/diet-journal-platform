# Android / iOS 饮食推荐 App 设计

日期：2026-10-13

状态：待用户书面审阅；本文件不是实施计划，也不表示代码已经实现。

## 1. 目标与背景

为现有高血压饮食推荐系统增加 Android 和 iOS 普通用户客户端，供毕业设计和内部真机演示使用。客户端复用现有 FastAPI、PostgreSQL、推荐 worker、账户及菜谱数据；不直接访问数据库或 Ollama。管理功能继续留在网页后台。

首版验收目标是在至少一台 Android 和一台 iPhone 上安装并完成登录、档案维护、查看今日菜谱、发起饮食聊天、查看推荐历史、查看菜谱详情、记录血压和登出。演示资料使用合成用户档案，不录入真实患者资料。推荐系统仍是演示用途，不宣称临床验证或诊断能力。

## 2. 已确认的产品范围

- 仅允许预先建立的 50 个演示账户登录，不提供注册入口；使用现有本地数据库账户。
- 面向普通用户；管理员继续用网页后台。
- 界面支持中文、英文和日文。档案包含个人税前年收入档次（日元）、预算、健康与过敏信息、饮食偏好和烹饪时间。
- 主要页面为登录、今日、聊天、历史、我的和菜谱详情。我的页面包括档案、血压记录、语言、改密和登出。
- 血压功能只记录和显示，不据此作诊断或修改治疗。
- 聊天仍由服务端执行饮食范围判断。当前会话确认的非饮食固定回复是“无法回答与饮食无关的内容”，客户端逐字显示服务端结果。
- 首版不做公开商店发布、移动管理后台、注册、推送通知、支付、离线推荐、实时商品价格或健康诊断。

### 与现有路线图的文字差异

`docs/PROJECT_ROADMAP.zh-CN.md` 记录了较早的多语言、带说明的非饮食拒答方案。本次移动端设计过程中，用户再次明确并确认固定中文回复，因此本设计采用固定回复；实施时需将后端 `outside_diet_scope` 响应与该决定同步，且不得由客户端追加前后缀或翻译。该明确确认优先于路线图中的旧说明。

## 3. 技术路线

采用独立 `mobile/` Expo／React Native TypeScript 客户端，使用 Expo Router 组织登录路由、底部主导航和详情页。网页现有 React/MUI 组件不能直接作为原生 UI 复用；移动端单独维护界面和依赖，通过后端接口共享业务数据。API 类型应集中维护，并以 FastAPI OpenAPI 契约作校验依据。

已考虑的方案：

1. **Expo／React Native（选定）**：一套 TypeScript 客户端覆盖 Android 和 iOS，适合现有 React 技术背景，并可从 Linux Spark 触发 EAS 云端构建。
2. **Capacitor 包装网页**：初期页面复用更多，但 WebView 会限制原生交互，并使移动端认证和键盘行为更难维护。
3. **Kotlin 与 Swift 分别原生开发**：平台能力最直接，但需要维护两套客户端，超出当前毕业设计演示的合理工作量。

客户端、API 与本机服务的边界：

```text
Android / iOS
    │ HTTPS + Bearer 会话令牌
    ▼
Spark 上的 FastAPI API
    ├── PostgreSQL：用户、档案、会话、任务、菜谱、推荐历史
    ├── 推荐 worker：聊天理解、约束检查、饮食计划与证据解释
    └── Ollama / pgvector：仅由服务器内部服务访问
```

`mobile/` 使用独立 `package.json` 和构建配置；移动端首版不改造为前后端共享 UI 的 monorepo。网页、后台、数据库结构和 Ollama 模型部署继续独立运行。

## 4. 身份认证与接口契约

当前网页认证是 HttpOnly Cookie + CSRF，`app_sessions` 已存令牌哈希并使用 12 小时过期时间。移动端增加专用登录和登出接口，例如 `POST /api/auth/mobile/login` 与 `POST /api/auth/mobile/logout`；登录沿用现有账户校验和速率限制，返回随机高熵令牌、过期时间及用户基本信息。服务端只在现有会话表保存令牌哈希。移动端认证通过 `Authorization: Bearer`，不使用浏览器 Cookie；`require_user` 同时支持两种客户端认证。网页 Cookie 请求仍必须通过现有 Origin/CSRF 检查。密码修改、管理员禁用账户和登出继续撤销数据库会话。

首版不增加刷新令牌；令牌过期后重新登录。令牌通过 Expo SecureStore 保存并在登出时删除。档案、对话文本和推荐历史只在使用时保留于应用内存，服务端为唯一事实来源，不做离线缓存。

移动端使用的现有接口：

| 功能 | API |
|---|---|
| 登录态和账户 | `/api/me`、新增移动端登录/登出、`/api/auth/password` |
| 今日与菜谱 | `/api/home/today`、`/api/recipes`、`/api/recipes/{id}`、`/api/recipe-images/{id}` |
| 档案与食品偏好 | `/api/profile`、`/api/income-bands`、`/api/foods`、`/api/foods/{code}` |
| 血压记录 | `/api/blood-pressure` |
| 聊天与会话 | `/api/diet-chat/messages`、`/api/diet-chat/sessions`、`/api/diet-chat/sessions/{id}` |
| 计划任务、历史与证据 | `/api/recommendation-jobs`、`/api/recommendation-jobs/{id}`、`/api/recommendation-jobs/{id}/cancel`、`/api/recommendations`、`/api/recommendations/{id}`、`/api/recommendations/{id}/substitutions`、`/api/evidence/{id}` |

所有用户数据由后端按当前账户授权。移动端不开放管理员接口，不信任客户端传来的 user ID、权限、营养量、价格或来源页码。

## 5. 页面和行为

底部四个主入口为“今日、聊天、历史、我的”；登录独立于主导航。菜谱详情从今日、聊天结果或历史页进入。

| 页面 | 关键行为 |
|---|---|
| 登录 | 账户 ID 与密码；没有注册链接；凭据错误和服务不可用分别提示 |
| 今日 | 显示东京日期、菜谱图片卡片及可用的营养/预算摘要；未完成个性化条件时将卡片标为“示例，非个性化推荐”并链接到需补充的档案信息 |
| 聊天 | 新对话、已有会话、饮食示例提示；显示排队/处理中/结果；服务端返回的非饮食固定句原样显示 |
| 历史 | 显示推荐时间和保存的方案快照；可查看详情并按已有接口更换一餐 |
| 我的 | 分区编辑基础档案、年收入和每日预算、健康/过敏、饮食偏好、烹饪时间；语言、血压记录、修改密码、登出 |
| 菜谱详情 | 显示食材、份量、做法、过敏信息、营养与估算花费、来源证据；示意图片必须标注为示意图 |

过敏档案明确显示“未确认、无过敏、存在过敏”状态；不能把空值呈现为“无”。档案保存沿用 `expected_version`，遇到 409 时要求刷新确认，不能静默覆盖。营养或价格信息缺失时如实标注，不以零值替代。

## 6. 任务与异常状态

聊天和推荐提交返回 HTTP 202 及任务 ID，之后由客户端轮询任务接口，直到任务离开 `queued`/`running`。轮询是首版唯一状态传输机制；不增加 WebSocket 或推送。客户端回到前台时再读一次任务状态。用户可取消仍在排队或运行中的任务；网络重试必须复用原幂等键。

客户端区分任务传输状态和业务结果：

- `ready`：展示经过后端计算和验证的结果。
- `needs_clarification`：指出缺少或未确认的资料并引导补充。
- `unsupported`：解释当前演示规则未覆盖，不伪装成正常推荐。
- `out_of_scope`：显示服务端固定回复。
- `infeasible`：解释当前约束组合无解，不擅自放宽健康或过敏限制。
- `failed` / `cancelled`：说明失败或取消，并提供可行的重试方式。

HTTP 401 清除本机令牌并回到登录；422 显示字段校验；409 档案冲突提示刷新；429 提示任务队列繁忙；网络或 5xx 错误不得产生虚构推荐。发送中页面保留用户输入，支持安全重试。

## 7. 安全与演示数据

- 真机使用前，为 Spark API 配置 HTTPS 反向代理和设备可验证的证书；应用不得通过发布版明文 HTTP 传输密码、健康档案或令牌。
- 防火墙只允许授权局域网或受控 VPN 访问 API；PostgreSQL 和 Ollama 保持在服务器内部，不向手机暴露端口。
- 令牌只放在系统安全存储；不写入日志、埋点或崩溃报告。首版不增加第三方分析 SDK、推送和敏感信息本地持久缓存。
- 演示只用合成档案。菜谱、营养、预算和证据需保持“演示/估算”标识，不能宣称医学审核或临床有效性。
- EAS 内部分发下载配置为需授权 Expo 账号；不要把未受限构建链接当作访问控制。

## 8. 测试和发行验收

自动化测试覆盖：Cookie + CSRF 既有登录路径回归；移动令牌创建、过期、撤销、密码修改后的失效、停用账户拒绝访问；不同用户之间档案、聊天、任务、血压、历史隔离；无注册入口；档案 409、任务幂等键与各业务终态；固定非饮食拒答；语言和 `unknown/none/present` 过敏状态。

Android 和 iOS 真机验收均走通：登录、补全档案和收入档次、查看今日卡片、聊天中提出饮食请求和非饮食请求、查看推荐历史与详情、记录血压、登出；另验证 HTTPS 证书、断网恢复、键盘遮挡、系统字号、读屏焦点和任务取消。应用不得将未确认的示例菜谱显示为个人方案。

使用 EAS 云构建：Android 内部分发生成可直接安装的 APK，并启用授权下载；iOS 使用 TestFlight 或 Ad Hoc。iOS 真机签名分发需要 Apple Developer Program 账号；Ad Hoc 还需登记每台测试设备 UDID。用户目前没有或不确定是否有该账号，因此这是外部前置条件；获得账号前可以继续客户端开发与 Android 内测，但不能承诺可交付 iOS 安装包。公开上架不在本项目首版范围内。

## 9. 实施边界与未决前置条件

该设计是一个完整的移动用户端子项目，可按阶段实施：先处理 API HTTPS 与移动认证，再搭建客户端登录/导航，然后接首页与档案、聊天任务、历史/详情，最后完成跨平台回归和内部分发。实施计划应包含后端兼容测试、移动端测试和发行验收，不应先替换现有 Web 或重写推荐 worker。

实施开始前仍需落实：

1. Expo 账号及 EAS 项目归属；
2. Apple Developer Program 账号是否具备或需申请，以及用于测试的 iPhone UDID/TestFlight 测试组；
3. Spark HTTPS 证书和手机可访问的 API 主机名/网络方案；
4. 至少一台 Android 和一台 iPhone 真机用于最终验收。

以上依赖不改变已选客户端架构；未具备 iOS 签名条件时，不阻塞其余开发和 Android 验收。
